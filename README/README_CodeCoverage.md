# Code Coverage

## Tools Referenced

- coverlet https://github.com/coverlet-coverage/coverlet (MIT) - `coverlet.collector`, already referenced by both test
projects. It's the data collector behind `dotnet test --collect:"XPlat Code Coverage"`.
- ReportGenerator https://github.com/danielpalme/ReportGenerator (Apache-2.0) - a **.NET tool**, pinned in the repo's
local tool manifest [`dotnet-tools.json`](../dotnet-tools.json). It turns coverlet's raw XML into readable reports.
ReportGenerator also sells an optional PRO license / GitHub sponsorship that unlocks extra features. Nothing in this
chapter needs it (see the method coverage note below).

Configuration: [`coverage.runsettings`](../coverage.runsettings) at the repo root.  

There are no NUnit tests specific to this chapter. Code coverage measures the tests that already exist, across every
chapter.  

**See also:** [Mutation Testing](./README_MutationTesting.md). Coverage and mutation testing answer different
questions, and this chapter compares them on the same code.  

---

## What does code coverage measure?

Which parts of the production code ran while the tests ran:

- **Line coverage** - the percentage of executable lines that ran at least once.
- **Branch coverage** - the percentage of decision outcomes taken (both the `true` and `false` side of an `if`,
each arm of a `?:`, and so on). This is usually the more telling number: a line with an `if` on it counts as
"covered" even when only one side of the condition was ever tested.

What it does **not** measure is whether any test would *notice* if that code were wrong. A test with no assertions
still produces coverage. That's the gap [Mutation Testing](./README_MutationTesting.md) fills.

## How do I collect coverage?

```
dotnet test UnitTestingCookbook.sln --settings coverage.runsettings --collect:"XPlat Code Coverage" --results-directory TestResults
```

Each test project writes its own `TestResults/<guid>/coverage.cobertura.xml`, so this repo produces two: one from
`UnitTestingCookbook.Tests` and one from `UnitTestingCookbook.TestHelpers.Tests`. coverlet automatically leaves the
test assemblies themselves out, so what's measured is the code under test: `UnitTestingCookbook.MinimalApi`,
`UnitTestingCookbook.Support`, and `UnitTestingCookbook.TestHelpers`. (`TestResults/` is git-ignored.)

To measure only some tests, add the same `--filter` you'd use with `dotnet test`. CI, for example, excludes this repo's
by-design failing tests with `--filter "TestCategory!=_fails&TestCategory!=_false_negative"`.

---

## How do I turn that into a readable report?

```
dotnet tool restore     # once - installs the version pinned in dotnet-tools.json
dotnet reportgenerator -reports:"TestResults/**/coverage.cobertura.xml" -targetdir:CoverageReport -reporttypes:"Html;TextSummary"
```

ReportGenerator **merges** the per-project XML files into one report. Open `CoverageReport/index.html` to see every
class with each source line highlighted green (covered), red (not covered), or yellow (only some branches covered).
`CoverageReport/Summary.txt` is the same thing as plain text. (`CoverageReport/` is git-ignored.)

## How do I control what counts?

<!-- snippet: CoverageRunSettings -->
<a id='snippet-CoverageRunSettings'></a>
```xml
<RunSettings>
  <DataCollectionRunSettings>
    <DataCollectors>
      <DataCollector friendlyName="XPlat code coverage">
        <Configuration>
          <Format>cobertura</Format>
          <!-- Auto-properties ({ get; set; }) have no logic to test - counting them only adds noise, in either direction. -->
          <SkipAutoProps>true</SkipAutoProps>
          <!-- Code marked [ExcludeFromCodeCoverage] or generated by the compiler/tools isn't counted. -->
          <ExcludeByAttribute>ExcludeFromCodeCoverage,GeneratedCodeAttribute,CompilerGeneratedAttribute</ExcludeByAttribute>
        </Configuration>
      </DataCollector>
    </DataCollectors>
  </DataCollectionRunSettings>
</RunSettings>
```
<sup><a href='/coverage.runsettings#L4-L20' title='Snippet source file'>snippet source</a> | <a href='#snippet-CoverageRunSettings' title='Start of snippet'>anchor</a></sup>
<!-- endSnippet -->

- **`SkipAutoProps`** - auto-properties (`{ get; set; }`) have no logic, so they're left out. They distort the numbers
in **both** directions: in this repo they accounted for 46 coverable lines, 34 covered and 12 never touched. Measured on
the same test run, with and without this setting:

| | Without `SkipAutoProps` | With `SkipAutoProps` |
|---|---|---|
| Coverable lines | 554 | 508 |
| Line coverage | 92% | 93.7% |
| Branch coverage | 75.4% (77 of 102) | 79.7% (75 of 94) |

- **`ExcludeByAttribute`** - leaves out code marked `[ExcludeFromCodeCoverage]`, plus code generated by the compiler or
by tools. Use `[ExcludeFromCodeCoverage]` sparingly, and give a reason
(`[ExcludeFromCodeCoverage(Justification = "...")]`). Otherwise it becomes a way to quietly make the number go up.

**NOTE:** CI builds in **Release**, where the same tests report **93.4% (354 of 379 lines)**. The optimizer changes

The interesting part isn't the headline number. It's the classes **below** 100%, and *why* each one is below. Three of
them show three very different reasons:

### 1. A real gap: `OfferValidator` (81.2%)

The report highlights the invalid-`PaymentType` branch in red: no test ever passes something other than `"P"` or
`"L"`. That's a genuinely missing test, the thing coverage is best at finding. (This class was added with the
[Test Data Builders](./README_TestDataBuilders.md) chapter, and coverage found the gap while this chapter was being
written.)

<!-- snippet: OfferValidator.cs -->
<a id='snippet-OfferValidator.cs'></a>
```cs
using UnitTestingCookbook.Support.Models;

namespace UnitTestingCookbook.Support.Services;

public static class OfferValidator
{
    public const int MaxLeaseTerms = 36;

    public static IReadOnlyList<string> Validate(Offer offer)
    {
        List<string> errors = [];

        if (offer.Finance.PaymentType is not ("P" or "L"))
        {
            errors.Add("PaymentType must be P (purchase) or L (lease).");
        }

        if (offer.Finance.PaymentType == "L" && offer.Finance.MaxTerms > MaxLeaseTerms)
        {
            errors.Add($"Lease terms cannot exceed {MaxLeaseTerms} months.");
        }

        if (offer.Finance.DownPayment < 0)
        {
            errors.Add("DownPayment cannot be negative.");
        }

        return errors;
    }
}
```

### 2. A gap hidden by deferred execution: `ExtensionMethods` (40%)

`SplitAndKeep()` is only called by one test, and that test only checks that a `null` input throws:

<!-- snippet: AwesomeAssertionsTests_O_IEnumerableYield -->
<a id='snippet-AwesomeAssertionsTests_O_IEnumerableYield'></a>
```cs
public void O_IEnumerableYield()
{
    // Arrange
    const string? input = null;

    // Act
    Func<IEnumerable<string>> action = () => input!.SplitAndKeep(new char[] { ' ' });

    // Assert
    action.Enumerating().Should().ThrowExactly<ArgumentNullException>();
}
```
<sup><a href='/UnitTestingCookbook.Tests/AwesomeAssertionsTests.cs#L377-L389' title='Snippet source file'>snippet source</a> | <a href='#snippet-AwesomeAssertionsTests_O_IEnumerableYield' title='Start of snippet'>anchor</a></sup>
<!-- endSnippet -->

The method's real work happens in a local `yield` iterator, and that code only runs when someone *enumerates* the
result with valid input. No test does, so the splitting logic has never run under test. The null-argument checks
run eagerly, so the method *looks* tested at a glance. The line-by-line report makes the difference obvious.

### 3. Not a gap at all: `ShippingCalculator` (70%)

[`ShippingCalculator`](../UnitTestingCookbook.Support/Services/ShippingCalculator.cs) is the class the Mutation
Testing chapter tests thoroughly. Its only method, `Calculate()`, is **100%** covered, every line and every branch.
The class still reports 70% because of its constants:

<!-- snippet: ShippingCalculator.cs -->
<a id='snippet-ShippingCalculator.cs'></a>
```cs
namespace UnitTestingCookbook.Support.Services;

public static class ShippingCalculator
{
    public const decimal FreeShippingThreshold = 50m;
    public const decimal StandardRate = 5.99m;
    public const decimal ExpressSurcharge = 10m;

    public static decimal Calculate(decimal orderTotal, bool isExpress)
    {
        if (orderTotal < 0)
        {
            throw new ArgumentOutOfRangeException(nameof(orderTotal), orderTotal, "Order total cannot be negative.");
        }

        decimal shipping = orderTotal >= FreeShippingThreshold ? 0m : StandardRate;

        return isExpress ? shipping + ExpressSurcharge : shipping;
    }
}
```
<sup><a href='/UnitTestingCookbook.Support/Services/ShippingCalculator.cs#L1-L20' title='Snippet source file'>snippet source</a> | <a href='#snippet-ShippingCalculator.cs' title='Start of snippet'>anchor</a></sup>
<!-- endSnippet -->

The three uncovered lines are the `const decimal` declarations. A `decimal` can't be stored as a true constant in
.NET's compiled code (IL), so C# compiles `const decimal` into a `static readonly` field marked with
`[DecimalConstant]`, initialized by a static constructor, and copies the *value* everywhere the constant is used. The
fields are never actually read, so the static constructor never runs, and coverlet reports those three lines as
never executed. (Verified by reflection: the `const decimal` field has `IsLiteral = False`, `IsInitOnly = True`, and
the class has a static constructor, while a `const int` in the same class is a true literal.)

The fix is to **read the line-by-line report**, not to change the production code to satisfy the tool.

## Is 100% coverage the goal? Coverage vs. mutation testing

No. Here's the same class measured both ways, using the same two test sets as the
[Mutation Testing](./README_MutationTesting.md) chapter:

| `ShippingCalculator.Calculate()` | Lines run | Branches taken | Mutation score (Stryker) |
|---|---|---|---|
| Happy-path test only (`A_HappyPath_Only`) | 71% (5 of 7) | 67% (4 of 6) | **50%** |
| All five tests (`A_` - `E_`) | **100%** | **100%** | 91.67% |

- With only the happy-path test, coverage looks respectable, but half the deliberately broken versions of the code
still pass every test.
- With all the tests, coverage is a perfect 100%, yet Stryker still finds a change no test notices (the exception
message, deliberately left that way - see the Mutation Testing chapter).

Coverage tells you what code **ran**. Mutation testing tells you what code is actually **checked**. Low coverage is
always a warning sign, but high coverage alone proves very little.

## How does CI use it?

CI ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) collects coverage on its normal test run, then:

- adds a ReportGenerator `MarkdownSummaryGithub` table to every run's **Summary** page (pushes *and* pull requests), and
- on every push to `main`, publishes the full HTML report to **GitHub Pages**:
**https://keithmccreery.github.io/UnitTestingCookbook/**. That's the same report as `CoverageReport/index.html`
locally, and it's linked from the repo's *About* box and from the coverage badge at the top of the main
[README](../README.md) (ReportGenerator's `Badges` report type generates the badge image too).

Pull requests never publish, so the site always reflects `main`. The `deploy-coverage` job is the only part of the
workflow with permission to write to Pages.

It's all **informational only**: there's no minimum threshold, and coverage never fails the build. A hard threshold
tends to get met by adding assertion-free tests or `[ExcludeFromCodeCoverage]`, which defeats the purpose. (coverlet's
MSBuild integration, `coverlet.msbuild`, does support thresholds if you want them; the `coverlet.collector` data
collector used here doesn't.)

**NOTE:** In the Markdown summary, ReportGenerator shows *method* coverage as "Feature is only available for sponsors"
- method coverage in that report type is part of its PRO tier. Line and branch coverage, which this chapter uses, are
free.
